# Local renovation assessment with Ollama

Use the installed Gemma 4 12B to draft a property’s renovation scope from saved evidence and selected photos. Keep Moondream as the fast first pass for room labels and short captions. Build the dollar range from dated local rates, measured quantities and the existing deterministic calculator. Use a human-reviewed scope before publishing. Gemma 4 31B is a candidate for difficult cases if it earns its extra runtime on this Mac.

## Fit the current pipeline

- `bulk_moondream.py` persists room categories and short captions to MongoDB. The existing `categorize_photos.py --local` path already selects an Ollama provider. Its single-listing assessment in `active_listing.py` samples up to 64 photos and asks the model for broad Bay Area prices and resale estimates. Preserve that earlier path as a private comparison while building a sourced estimate for reviewers.
- Use the resumable photo work and refresh logic in `buyer_worker.py` as the starting point for a local assessment executor. Its fixture executor already tracks images, rights, cache reuse, budget and versions. Save a room observation with a photo ID, label, visible evidence and uncertainty. Deduplicate repeated room angles and carry missing-photo and unverified-quantity states through to the final scope.
- Ask Gemma for a small schema containing room, task code, scope alternative, supporting photo IDs, quantity with its basis, confidence and inspection questions. Distinguish observed conditions from seller-reported issues. Map each task code to a dated, geography- and finish-specific price book, bid or invoice in code. Missing and unsupported prices stay unpriced and mark the result partial. Keep cosmetic and full replacement scopes mutually exclusive and keep quantities such as roof area unknown until verified.
- Validate evidence IDs, task codes, provenance, quantities and mutually exclusive choices before using `buyer_analysis.py` and `renovation_costs.py` to extend unit prices and reconcile totals. Review candidates before publication. Preserve the model digest, prompt/schema version, gallery and rights snapshot and price-book version so a price-book change can reprice accepted scopes without calling the model again. Keep comps, valuations and underlying public-source permissions subject to the public Atlas display policy.
- Bind the inference adapter to the installed local service and require the appropriate source and listing AI rights before dispatch. Recheck rights before save and before publication. Keep the model out of web requests, give the worker only the evidence it needs and avoid logging photo bytes or raw remarks. The documented Ollama JSON-schema feature depends on the runner. The current Gemma MLX adapter passes the schema in the prompt and parses JSON in Python. Test format support for each installed tag and backend before relying on API-side enforcement. Server-side validation applies in either case. [Ollama structured outputs](https://docs.ollama.com/capabilities/structured-outputs) · [Current inference adapter](photo_inference.py) · [Buyer review workflow](../flip_ui/REVIEW_WORKFLOW.md)

## Benchmark on this Mac

1. Build a private set of about 12 homes with reviewed evidence. Include the Fairfield bath-scope and roof case, dated-but-usable rooms, repeated angles, large galleries, restricted or missing media, and completed projects with matched bids or paid invoices. Keep a small development subset and a held-out set grouped by property. For each case freeze the images and resize, captions, allowed task codes, provenance, rights and prompt. Keep held-out final costs outside every prompt.
2. On identical evidence, compare a deterministic scope-rule baseline, Gemma 12B using the saved observations, and Gemma 12B using the same observations plus selected photos. Compare Gemma 31B on the same holdout where it fits and add Qwen3-Coder only on the text input. Use the configured Haiku model on the same schema and evidence after approval, or label any archived legacy output as a different workflow. Score blindly against human-reviewed scope decisions and cost evidence.
3. Keep one property request in flight to start. Use a measured context budget, such as 4K for compressed evidence and 8K only if needed, with generation bounded to the schema. Include space for image and output tokens. Record tags, digests, quantization, runner, reasoning mode, temperature, context, photo count and resolution. Test a cold run and repeated warm runs. Measure elapsed time, model load, prompt and output tokens/durations, invalid/truncated responses, CPU/GPU placement, memory pressure and swap delta. Measure first with the backfill idle and then with the normal Moondream workload for the 12B. Schedule 31B or Qwen during a separate window if it displaces Moondream or adds sustained swap. Ollama can reserve more context memory for parallel requests. [Ollama chat metrics](https://docs.ollama.com/api/chat) · [Ollama model scheduling](https://docs.ollama.com/faq)
4. Report evidence-grounded included/missed tasks, false costly repairs, unsupported quantities or claims, missing-work detection, valid first-pass JSON and reviewer minutes. Calculate item and total dollar error and interval coverage only where scope aligns with verified bids or paid invoices. Report the size of that subset. Make exact calculator reconciliation and no invented evidence release gates. Keep missing-cost cases partial. Report P50/P95 time per completed home and availability separately from per-call token speed.
5. If the holdout supports 12B and the Mac handles concurrent work, run the existing rights-cleared 100-home pilot before scaling. Estimate hours from observed successful homes per hour and the eligible queue, then apply retries and measured cache reuse. For hosted test cases, calculate charges from metered input and output tokens. Local inference has no per-token API charge. Wall-clock occupancy, power, and reviewer time still matter. Run only the local evidence test until provider rights and a budget are supplied.
